# 项目范围与进度

本文档合并原“需求分析、开发计划、最终交付清单、宣讲进度对齐”的内容，作为项目当前范围、实际进度、缺口和交付检查的唯一入口。完整官方要求见 [00-比赛要求.md](00-比赛要求.md)，mock 数据说明见 [15-Mock数据说明.md](15-Mock数据说明.md)。

## 项目定位

本项目面向 C 端消费者，目标是把“拍照识物 -> 商品召回 -> 跨平台比价 -> 自然语言筛选 -> 购买建议”串成一条可演示、可解释、可扩展的购物决策链路。

核心用户故事：

```text
作为用户，
我希望拍摄一个商品或输入购物需求，
系统能够识别商品、搜索同款、比较价格、分析历史趋势，
并基于证据链告诉我当前是否值得购买。
```

主流程：

```text
imageId -> recognitionId -> searchTaskId -> comparisonId -> recommendationId
```

## MVP 范围

| 类型 | 内容 |
| --- | --- |
| 必须覆盖 | 登录注册、图片上传/拍照、商品识别、建议卡片、自然语言筛选、推荐列表、排序、比价、推荐理由和 evidence |
| 数据策略 | 默认使用 `mock` 商品、价格、历史价格和评价摘要数据；真实官方 API 作为加分项，不阻塞主链路 |
| 端侧策略 | 当前主演示采用 Web/PWA 演示端，支持浏览器相机能力；Flutter 移动端已具备分包主链路、搜索结果操作面板和接口契约检查，但完整真机/模拟器验收作为后续扩展 |
| AI 策略 | AI 编排在服务端完成；默认 mock provider，Ark 可选，失败时规则或 mock fallback |
| 暂缓实现 | 自动下单、复杂优惠叠加、大规模真实电商数据接入、长周期价格监控通知、完整原生 App |

非功能要求：

- 推荐结果必须可解释，价格和商品信息不能由大模型凭空编造。
- 前端不能直接传入 `user_id` 决定数据归属，后端必须从登录态解析当前用户。
- 不同用户之间的图片、识别记录、搜索任务、收藏、推荐记录必须隔离。
- 数据源必须合法；禁止爬虫、非法采集和违反平台服务条款的数据获取。

## 第一次宣讲补充要点

| 主题 | 补充结论 |
| --- | --- |
| 核心链路 | 重点打通“识别 -> 检索 -> 决策”，而不是只做以图搜图页面 |
| AI 能力 | 评委关注 VLM 视觉解析、LLM 意图理解、Prompt 结构化输出和服务端 AI Pipeline 编排 |
| 建议卡片 | 不应只是固定按钮堆叠，最好由识别结果、商品类型和当前上下文动态生成 |
| 数据源 | 允许使用 mock 数据或合法公开 API；禁止爬虫、非法采集和违反平台服务条款的数据获取 |
| 商品类型 | 类目越丰富越好；也允许聚焦某一类目，但要把体验和实现效果做扎实 |
| 功能触发 | 拍照识物、建议卡片、自然语言筛选等功能不强制必须在同一个触发点完成，只要功能点能完整演示即可 |
| 答辩关注 | 评委会围绕工程实现、模块边界、AI 调度、Prompt 设计和成员真实贡献追问 |

## 演示与交付检查

### 标准演示路径

1. 启动后端和前端。
2. 可先点击“一键演示主链路”确认完整链路可用，并观察左侧主链路进度是否全部完成、顶部决策摘要是否生成推荐结论。
3. 手动讲解时注册或登录。
4. 选择演示场景后点击示例图，或打开相机拍照。
5. 上传并识别，展示识别结果和建议卡片。
6. 点击建议卡片，或输入“1000 元以内的黑色款，要评价 4.8 分以上，只看官方”。
7. 切换综合、低价、销量、好评排序。
8. 选择 2-4 个商品生成比价。
9. 点击商品卡“洞察”，展示价格走势和评价风险。
10. 点击“提醒”设置目标价，或点击“收藏”后在购物资产中查看。
11. 点击生成推荐，展示 Agent 决策分、六步决策轨迹、候选胜因/败因矩阵、推荐理由、风险和 evidence。
