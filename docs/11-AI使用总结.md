# AI 使用总结

本项目把 AI 用在“理解意图”和“组织决策过程”，而不是让模型凭空生成商品事实。价格、评分、历史低价、评价风险和候选商品都来自后端数据源；AI 输出进入结构化校验后才参与流程。

## 使用位置

| 位置 | AI/规则能力 | 输入 | 输出 | 代码证据 |
| --- | --- | --- | --- | --- |
| 图片识别 | Ark VLM 可选，mock fallback | 用户上传图片 | `category`、`brand`、`model`、`keywords`、`attributes`、`confidence` | `ArkRecognitionProvider`、`MockRecognitionProvider` |
| 自然语言 refine | Ark LLM 可选，规则 fallback | “1000 元以内、黑色、评分 4.8、只看官方”等文本 | 白名单 `filters` 和 `notices` | `ArkRefineProvider`、`RuleBasedRefineProvider`、`FilterSanitizer` |
| Agent 决策 | 服务端证据计算 | 搜索任务、候选商品、历史价格、评价摘要 | `decisionScore`、`decisionSignals`、`decisionTrace`、`candidateAnalyses` | `ShoppingService` |
| 证据报告 | 服务端报告生成 | 已保存推荐记录和搜索任务 | Markdown 决策证据报告 | `GET /api/agent/recommendations/{id}/report` |
| AI Coding | 辅助架构梳理、代码修改、测试补强、文档整理 | 项目代码、赛事要求、运行结果 | 可运行功能、自动化测试、答辩材料 | 本仓库提交变更与 smoke test |

## Prompt 设计

### 图片识别 Prompt

系统 Prompt 约束模型身份和输出边界：

```text
你是电商拍照识物助手。只输出 JSON，不要输出 Markdown。
字段固定为 category, brand, model, keywords, attributes, confidence, explanation。
confidence 为 0 到 1。attributes 是对象，优先包含 color、style、scenario、keySpecs。
```

期望输出：

```json
{
  "category": "吹风机",
  "brand": "LumaCare",
  "model": "HD-001",
  "keywords": ["低噪音", "宿舍"],
  "attributes": {
    "color": "黑色",
    "scenario": "宿舍"
  },
  "confidence": 0.86,
  "explanation": "根据图片外观和文字标识判断"
}
```

### 自然语言筛选 Prompt

系统 Prompt 限定 `filters` 字段范围：

```text
你是电商搜索条件解析器。只输出 JSON 对象，字段只能包含 filters 和 notices。
filters 只能包含 maxPrice, minPrice, color, brand, category, minRating,
officialOnly, selfOperatedOnly, sortBy, platforms。
sortBy 只能是 comprehensive, price_asc, sales_desc, rating_desc。
platforms 只能包含 jd, taobao, pdd, tmall, other。
```

期望输出：

```json
{
  "filters": {
    "maxPrice": "1000.00",
    "color": "黑色",
    "minRating": 4.8,
    "officialOnly": true,
    "sortBy": "rating_desc"
  },
  "notices": []
}
```

## 兜底与校验

| 风险 | 处理方式 |
| --- | --- |
| Ark 未配置 | 默认使用 `mock` 识别和规则 refine，主链路不依赖外部模型 |
| Ark 超时或返回非 JSON | 识别回退 mock，筛选回退规则解析 |
| 模型输出多余字段 | `FilterSanitizer` 只保留白名单字段 |
| 价格、评分、评价被模型编造 | 推荐阶段不读取模型生成的商品事实，只读取后端 mock/official_api 数据 |
| 用户输入条件过宽或无条件 | 后端保留综合排序，并用建议卡片引导低价、官方、自营、高评分、同色等动作 |

## Agent 决策机制

Agent 推荐不是单句“建议买”，而是服务端根据候选证据计算结构化结果：

- `decisionSignals` 固定覆盖意图匹配、价格位置、口碑质量、渠道可信、风险控制五类信号。
- `decisionScore` 按权重综合：匹配 28%、价格 24%、口碑 18%、渠道 14%、风险 16%。
- `decisionTrace` 输出识别意图、约束解析、商品召回、价格时机、风险审计、最终建议六步轨迹。
- `candidateAnalyses` 给每个候选生成排名、决策分、胜因、败因和 verdict，便于解释为什么选 A 而不是 B。
- `recommendation report` 将上述结果导出为 Markdown，但不重新调用 LLM，不新增商品事实。

耳机场景示例中，系统会比较：

- 官方标准价候选：价格适中、官方渠道明确。
- 京东自营候选：价格略高但履约和售后确定性更强。
- 官方补贴低价候选：价格最低但包装/售后风险更高。

这让答辩时可以展示“低价不是唯一目标，Agent 会在预算、渠道和风险之间做权衡”。

## AI Coding 使用方式

开发过程中，AI Coding 主要用于：

- 快速阅读和整理赛事要求，合并需求、进度、演示和交付文档。
- 根据现有 Spring Boot/静态前端结构补齐功能，而不是重写技术栈。
- 生成和修改后端测试，覆盖主链路、用户隔离、官方 API 未配置、候选矩阵和多类目 mock 识别。
- 构建 Web 主链路 Selenium smoke test，让演示质量可自动验证。
- 持续对齐文档与代码，避免“文档说未实现、代码已实现”的冲突。

AI Coding 的产物必须经过本地命令验证，不能只依赖代码生成结果。本项目当前保留的关键验证命令：

```powershell
cd backend
mvn test

cd ..
python scripts\run-web-demo-smoke.py --scenario headphones
node --check frontend\app.js
node --check frontend\service-worker.js
```

## 合规说明

- Ark、拼多多、京东等密钥不进入前端，不进入仓库，不写入截图或视频。
- 不实现非授权数据抓取，不绕过平台服务条款。
- mock 数据只用于演示功能闭环，不代表真实商品实时价格。
- official_api 只调用授权开放平台；未配置凭证时后端返回明确诊断，不静默爬取网页。
