# Agent 架构设计 — 图片内容

## 图 1：核心决策循环

- 标题：核心循环：观察 → 决策 → 执行
- 闭环节点：
  1. 主 Agent 观察
  2. 提出一个类型化动作
  3. 执行动作并结算用量
  4. 结果与证据校验
- 循环引出三个终态：追问用户 / 回答（带证据）/ 无结果结束

## 图 2：固定动作目录

- 标题：固定动作目录：模型只能选这 8 个动作
- 布局：三组动作卡片；每张卡片同时展示“使用时机”和一个 iPhone 示例
- 检索通道：
  - `search_and_compare` 主检索比较：首次需求已经足够明确时使用；例：「iPhone 15 Pro，256GB，7000 元内」→ 检索并比较候选
  - `supplement_search` 缺口补查：已有候选，但存在一个明确且单轮可补的查询缺口时使用；例：缺少京东候选 → 只补查「京东 iPhone 15 Pro 256GB」
  - `inspect_evidence` 证据检查：候选已经存在，只需读取已登记证据解释字段时使用；例：用户问「为什么这款判定为 128GB？」→ 检查容量证据
- 委派通道：
  - `delegate_research` 多步调查：需要连续搜索、检查证据、再比较时使用；例：国行版本表述不统一且首轮召回不足 → 委派 Research
  - `delegate_verification` 字段核验：某个候选的关键字段有争议；例：标题列出多个容量，但无法确认 6499 元对应哪个 SKU → 委派 Verification
- 终态通道：
  - `ask_user` 追问：需求缺少会改变检索结果的关键信息时使用；例：用户只说「帮我找刚才那台 iPhone」，但会话中没有对应候选 → 请求提供型号或图片
  - `answer` 回答：候选已满足硬约束且证据完整时使用；例：确认 iPhone 15 Pro 256GB 的当前 SKU、价格和来源后给出比较结果
  - `finish_no_results` 无结果：有效检索已完成，但没有候选满足硬约束时使用；例：所有 7000 元内候选都不是 256GB → 说明无符合结果和已检查范围

## 图 3：Subagent 委派

- 标题：按需 Subagent：单层、受限、可验证
- 顶部：MainAgent 主 Agent（维护购物目标 · 唯一状态写入者）
- 向下委派两个子 Agent：
  - ResearchSubagent 多步补查
  - VerificationSubagent 字段核验
- 子 Agent → 主 Agent 回程：结果重新验证后归并
- 委派时机（三个判定卡）：
  - 缺口简单，一轮能补 → 不委派，主 Agent 直接补查
  - 缺口复杂，需多步调查 → 委派 Research
  - 候选详情字段有争议 → 委派 Verification
- 为什么不直接调方法（对比说明）：
  - 直接补查：单轮、共享主状态、失败影响当前轮
  - 子 Agent：冻结约束 + 证据白名单 + 独立子预算 + 截止时间，多步探索关进沙箱，失败可整体丢弃
- 交互流程（调用与结果处理）：
  1. 主 Agent 提出 delegate 动作（只是提案）
  2. Runtime 校验准入，构建子任务：冻结约束 · 允许证据 · 子预算 · 截止时间
  3. 子 Agent 在隔离上下文跑自己的 观察 → 决策 → 执行 循环
  4. 返回 SubagentResult：facts 必须引用已登记证据
  5. 主 Agent 当不可信输入重新验证：事实绑定证据 · 可比性重算 → 归并进主状态

## 图 4：委派实例（数据模拟）

- 标题：什么时候委派：三个实例
- 布局：三栏并列，每栏 = 请求 → 首轮数据 → 决策 → 子 Agent 轨迹 → 结果

- 例 1：零委派
  - 请求：「iPhone 15 Pro，256GB，黑色，7000 元内」
  - 首轮数据：约束 { 类目: 手机 / 品牌: Apple / 型号: iPhone 15 Pro / 容量: 256GB / 价格 ≤ 7000 / 颜色: 黑 }；召回池 60 候选；gaps = 空
  - 决策：证据足够，直接 answer，零委派
  - 原因：没有缺口，子 Agent 无事可做

- 例 2：委派 Research
  - 请求：「iPhone 15 Pro，256GB，国行版，预算 7000」
  - 首轮数据：召回池仅少量候选；gaps = [ 国行版本表述不统一 / 召回不足 ]
  - 决策：缺口是多步的（先确认可用于检索的版本表述 → 按新表述补查 → 再比较），单轮补查不够 → 委派 Research
  - Research 轨迹：search_once「iPhone 15 Pro 256GB 国行」→ 候选 12 → 32；
                  inspect_evidence；
                  search_once「iPhone 15 Pro 256G 中国大陆版」→ 候选 → 45；
                  compare_candidates → finish
  - 返回：candidate_ids ×33；facts ×5 均引用已登记证据；recommendation = comparable
  - 主 Agent 处理：重验后归并，候选池 12 → 45，回答

- 例 3：委派 Verification
  - 请求：「帮我找 7000 元内的 iPhone 15 Pro 256GB，展示价格必须对应 256GB」
  - 首轮数据：候选 X 标价 6499 元，标题写「128GB / 256GB / 512GB 可选」，但当前 Offer 没有选中 SKU 的容量字段 → `storage = unknown`
  - 问题：商品标题列出 256GB 选项，不代表 6499 元对应的就是 256GB；这个价格也可能属于 128GB
  - 决策：需要核验候选 X 的当前 SKU 容量和价格口径 → 委派 Verification 查证
  - Verification 轨迹：调用已接入的商品详情接口，按候选 X 核验「当前 SKU 容量」「标价对应规格」→ 详情写明「当前 SKU：128GB；标价：6499 元」→ finish
  - 返回：facts = [ X: 当前 SKU 容量为 128GB ← 证据 e1；X: 6499 元对应 128GB ← 证据 e2 ]
  - 主 Agent 处理：逐条重验证据后，X 与“256GB”硬约束冲突，直接排除；只有详情确认当前 SKU 为 256GB 且标价属于该 SKU，才允许进入确认推荐
